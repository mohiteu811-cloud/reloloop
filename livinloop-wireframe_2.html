Principle — Show the math
AI valuation isn't a number, it's a derivation. Retail price, depreciation, condition multiplier — each one visible. If a user disagrees, they edit. Black-box estimates are the fastest way to break trust.
Principle — Asymmetric reservation
Proposing reserves your listing, not the recipient's. Prevents DoS attacks on inventory. Recipient stays liquid until they accept; the first accept atomically closes the door for all others.

Principle — Both pickups, both confirms
A swap isn't half-done when one side picks up. The completion semantics are dual-confirm — both parties tap "got it" before the loop registers as closed. Mismatched confirms surface in ops for review.
Principle — Loop's brand moment is the close
"Looped." is the most powerful word in the system. It appears once per swap, on the final screen, in the loop-sun color, after both confirms. Saying it everywhere drains its meaning. Saying it here makes it earn its keep.
§ 03 — The matching engine Same primitive · adapted for two-sided listings

How comparable becomes matched.

One primitive: a 768-dim vector embedding of every listing's photos + text, queried with cosine similarity. Layered with two filters specific to swaps — value within tolerance, geography bilateral or same-city. The composite ranks who gets surfaced first.

i. Capture
Photos + AI extract
Up to 4 photos, Gemini extracts brand, model, condition, dimensions, original retail. User-confirmed asking value.
→
ii. Encode
CLIP image + text
Mean-pooled image vectors concatenated with text encoder over title + brand + condition. L2-normalised. 768-dim.
[0.24, -0.41, 0.07, 0.88, 0.11, …]
→
iii. Store + match
pgvector + filters
HNSW index in Postgres. Match query joins on category, value tolerance, bilateral geography. Top-K under 30ms at 100k listings.

§ The three filters · combined into one composite
i. Semantic similarity
0.87 × 0.4
CLIP cosine over photos and title. Catches "both are 3-seat fabric couches with similar silhouettes" without keyword matching.
ii. Value alignment
0.94 × 0.4
Decays linearly with delta. Same value = 1.0; at tolerance boundary = 0.0. Couches' category tolerance is ±25%.
iii. Geography
1.00 × 0.2
Perfect bilateral inter-city = 1.0. Same-city = 0.5. One-sided = excluded entirely from results.
Composite
0.87 × 0.4 + 0.94 × 0.4 + 1.00 × 0.2 = 0.92
Rounded display: 91%. Sriram and Sarah see each other as the strongest match on each of their listing pages.
Principle — Three filters, one query
The match is computed in a single SQL pass with pgvector. No separate pipelines for value scoring or geography logic. Keeps the engine debuggable and the latency under 30ms.
Principle — Composite over single signal
Pure semantic match surfaces visually-similar but wrongly-priced items. Pure value match surfaces same-priced unrelated items. The composite punishes weakness in any of the three — and that's exactly what users mean by "comparable."
§ 04 — Schema Postgres + pgvector · Prisma · 13 tables

Thirteen tables. Two-sided by design.

Full schema in livinloop-schema.md. The spine below is the part that makes the swap mechanic work — every Listing is both an offering AND a wanted, geography is paired, valuation lives on the row.

§ 05 — Photo pipeline + APIs Carried from LivAround · server-side only

All AI runs server-side.

The architectural rule from prior mobile work: client uploads bytes, server does everything else. No on-device frame extraction. No on-device inference. Photos go via tus to R2, then BullMQ workers handle Gemini extraction, valuation, and CLIP embedding.

i. Client
Capture & upload
expo-camera or browser FileReader → tus resumable upload to R2. No compression, no frame extraction.
→
ii. Worker · Gemini
Extract + valuate
BullMQ worker pulls from R2. Gemini extracts brand/model/condition/dimensions/retail estimate. Server applies depreciation curve.
→
iii. Worker · CLIP
Embed + persist
After user publishes, CLIP encoder over images + text. Vector stored in Postgres. Listing flips PROCESSING → LIVE.
§ The handful of endpoints that drive the whole app
POST /api/listings Create draft. Returns listingId + presigned R2 upload URLs.
POST /api/listings/:id/publish Validate + flip DRAFT → PROCESSING. Triggers embedding worker.
GET /api/listings/:id/matches Top-K SwapMatch rows for this listing, ranked by composite.
POST /api/proposals Create proposal · listingAId, listingBId, optional message.
POST /api/proposals/:id/accept Recipient accepts. Locks both listings, creates Conversation, notifies both.
POST /api/conversations/:id/confirm-complete Dual-confirm step. Both parties tap to close the loop. Listings → SWAPPED.
Stack — boring on purpose
Next.js · Prisma · Postgres + pgvector · Auth.js (magic links) · BullMQ · R2 · tus.io · Gemini 2.5 Flash · CLIP via Replicate. Every component mature, swappable, well-documented.
Photo pipeline reused
tus → R2 → BullMQ + sharp + Gemini is carried verbatim from LivAround. Different Gemini prompt (item valuation vs room walkthrough), same plumbing. Saves ~2 weeks of build.
