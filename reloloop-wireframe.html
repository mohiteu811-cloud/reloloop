§ 03 — The matching engine Vector similarity · geographic routing

How comparable works.

The engine is one primitive: a 768-dimension vector embedding of every listing's photos and text, queried with cosine similarity. Everything else — geography, timing, route capacity — layers on top as filters.

§ The embedding pipeline · per listing
i. Capture
Photos + text
Up to 4 photos, AI-extracted title, category, condition, dimensions.
→
ii. Encode
CLIP + text encoder
Image and text encoders run server-side. Outputs combined into one 768-dim vector.
[0.23, -0.41, 0.07, 0.88, …]
→
iii. Store
pgvector index
Vector stored in Postgres with HNSW index. Cosine-similarity queries return in <30ms at 100k listings.

§ What this primitive unlocks
i. Buyer-side substitution
A buyer wants "a TV around $500." Both Sriram's and Mohit's TVs surface, ranked by match-fit. Higher fill rate per buyer.
ii. Pricing intelligence
Mohit lists his LG at $620. Sriram's comparable Samsung is $540. We warn Mohit he's 15% above the route's median. Better pricing → faster sale.
iii. Bundle suggestions
Two comparable sofas on the same Saturday AKL→CHC truck. Crown ops gets a bundle suggestion — pair them with two CHC buyers, fill the load. Better truck utilisation.
iv. Cross-direction routing
Someone moving CHC→AKL has a fridge listed in CHC. Mohit (AKL→CHC) wants a fridge in CHC. Crown's return run carries it back. Both moves get cheaper.

The whole engine, one primitive
Embedding similarity. The four behaviours above are query variants on the same vector index — not four separate systems.
Geography is the cheap filter
Vector queries are scoped by city + time-window first, similarity second. Avoids comparing TVs in Auckland to TVs in Wellington unless a route exists.
§ 04 — Schema Postgres + pgvector · Prisma

Fourteen tables. One extension.

Full schema, indexes, and migration notes live in the companion document. Here's the spine — every other table either describes a side of the marketplace, attaches metadata to listings, or records a state transition.

// The seven tables that matter most. Full schema in reloloop-schema.md. model User { id String @id @default(cuid()) email String @unique name String? moves Move[] listings Listing[] offers Offer[] } model Move { id String @id @default(cuid()) userId String fromCityId String? // null for buyers without origin toCityId String moveDate DateTime role MoveRole // SELLER, BUYER, BOTH wants String[] // category ids the buyer is after } model Listing { id String @id @default(cuid()) moveId String categoryId String title String condition Condition priceCents Int status ListingStatus // DRAFT, LIVE, RESERVED, SOLD photos Photo[] embedding ListingEmbedding? } model ListingEmbedding { listingId String @id vector Unsupported("vector(768)") // pgvector model String // e.g. "clip-vit-b-32" computedAt DateTime } model DeliveryRoute { id String @id @default(cuid()) fromCityId String toCityId String runDate DateTime capacityM3 Float allocatedM3 Float @default(0) }
Why pgvector, not a separate vector DB
100k listings is well inside pgvector's HNSW comfort zone. Keeping vectors in the same Postgres instance means joins with route, listing, and city data run as a single query.
Embedding is async
Listing creation does not block on embedding. A BullMQ worker picks up new listings and computes embeddings within ~30s — listing is browseable without it, just doesn't get matched until it's ready.
§ 05 — Photo pipeline + APIs Server-side · server-side · server-side

All AI runs server-side.

Hard-won lesson from prior mobile work: do not extract frames or run AI on the device. Upload the raw photos via tus to R2, let server workers handle Gemini vision and CLIP embedding. The client app stays small, fast, and crash-free across Android codec quirks.

§ The capture pipeline · per listing
i. Client
Capture & upload
expo-camera or browser FileReader → tus resumable upload to R2. No frame extraction, no compression decisions.
→
ii. Worker
Gemini vision + CLIP
BullMQ worker pulls from R2. Gemini extracts title, category, condition, dimensions. CLIP encodes the photo + text.
→
iii. Persist
Postgres + pgvector
Auto-fill fields on listing, vector on ListingEmbedding, thumbnails on Photo. Listing flips to LIVE.
§ The handful of endpoints that drive the whole app
POST /api/listings Create draft. Returns listingId, presigned R2 upload URLs.
POST /api/listings/:id/publish Flip status DRAFT → LIVE. Triggers embedding worker.
GET /api/feed Personalised buyer feed. Filters: city, category, max_price, arrival_by.
GET /api/listings/:id/comparables Top-K cosine neighbors in same category & route.
POST /api/listings/:id/offer Buyer makes an offer. Notifies seller in real time.
POST /api/bookings Commit purchase. Atomically reserves DeliveryRoute capacity.
Stack — boring on purpose
Next.js · Prisma · Postgres + pgvector · Auth.js (magic links) · BullMQ · Cloudflare R2 · tus.io. Every component is mature, well-documented, and easy to swap.
No client-side AI
All vision and embedding happens in the worker. The client uploads bytes. Lessons from prior mobile work — Android codec issues with on-device frame extraction caused weeks of pain. Don't repeat.
